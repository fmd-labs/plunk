A retried request is a duplicate email. A double-submitted checkout form is a double receipt. To make sure a request runs **at most once**, send an `Idempotency-Key` header.

If the key is new, Plunk processes the request normally. If your project has already used that key, Plunk does not perform the request a second time: it **refuses** it with `409`, or, for a `POST /v1/send` whose first request failed or never finished, finishes that request's work without sending any email twice.

These public API write endpoints support it:

- `POST /v1/track`
- `POST /v1/send`

`POST /v1/send/batch` takes a key per email instead (see [Batches](#batches)).

## Sending a key

The key is any string you choose, 1–255 printable ASCII characters. It must be unique per logical operation — a UUID, or something derived from your own data like `receipt-order-1234`.

## What happens on reuse

Reusing a key returns `409` with the error code `IDEMPOTENCY_KEY_REUSED`. The `details` object tells you about the request that originally claimed the key, and when both requests are a `POST /v1/send`, it lists the emails that request queued for the recipients of yours, in the same shape as a successful response's `data.emails`:

```json
{
  "success": false,
  "error": {
    "code": "IDEMPOTENCY_KEY_REUSED",
    "message": "Idempotency-Key \"receipt-order-1234\" has already been used",
    "statusCode": 409,
    "details": {
      "key": "receipt-order-1234",
      "originalRequest": "POST /v1/send",
      "originalRequestAt": "2025-01-15T10:30:00.000Z",
      "originalStatusCode": 200,
      "emails": [
        {
          "contact": {"id": "5d1c1ba6-4c1b-4f0e-9d2b-6f0a7c3e2b11", "email": "customer@example.com"},
          "email": "9a1f6f0e-8f39-5b5e-9c3f-2d7a4b8c1e55"
        }
      ]
    }
  }
}
```

An `originalStatusCode` of `null` means the original request is still in flight — two requests with the same key arrived at once, and this one lost the race. For `POST /v1/send`, `emails` then lists the emails it has queued so far; retry a little later for the complete list.

`POST /v1/track` refuses a reused key without returning the original event's ID. If you need that ID, record it when the first request succeeds.

## Retrying a send that failed

A `POST /v1/send` retried with the same key, after its first request failed or never answered, finishes that request instead of being refused. Each recipient's email is identified by the key and the recipient's address, so the retry reports the emails already queued without sending them again, sends the ones that are missing, and answers `200` with all of them.

This applies when the first request:

- answered with a `5xx`;
- answered with a `4xx` refusing one of its recipients, such as a marketing template for an unsubscribed contact, or the billing limit — fix the cause and retry with the same key;
- never answered, and started at least 30 seconds ago (the connection dropped or the server restarted). Until then the retry is refused with `409` as still in flight.

Retry with the same request: a recipient added in the retry is sent to, one left out is not reported, and a changed subject, body or data reaches only the recipients that had no email yet.

If you do not retry, the emails the first request created are still sent: Plunk queues an email left waiting without a job again after 15 to 20 minutes. An email still waiting a day after it was created is failed instead of sent late (self-hosters set the day with [`EMAIL_STALL_SWEEP_MAX_AGE_HOURS`](/self-hosting/environment-variables)). After a failed request, retry with the same key, never under a new key or with another provider: the emails the first request created would reach their recipients twice.

## Which failures free the key

Not every failed request burns the key.

| Outcome of the first request | Key is | Why |
| ---------------------------- | ------ | --- |
| `2xx` success | **Kept** | The operation happened. A retry would duplicate it. |
| `4xx` client error | **Released**, except as below | Validation and permission errors are rejected before anything is written, so it is safe to fix the request and retry with the same key. |
| `4xx` refusing a recipient of a send | **Kept** | The recipients before it may have their emails. A retry with the same key sends to the rest. |
| `5xx` server error | **Kept** | The request may have partially completed. A retry of `POST /v1/send` finishes it without duplicates; `POST /v1/track` refuses it. |

If a `5xx` on `POST /v1/track` burns a key for a request you're confident never went through, retry with a new key.

## Scope and expiry

Keys are scoped to your **project**, not to an endpoint. A key used on `/v1/track` cannot be reused on `/v1/send`. Two different projects can use the same key string independently. The keys of batch emails are kept apart: a batch email's key never collides with the same string sent as an `Idempotency-Key` header.

A claimed key expires after **24 hours**, after which it becomes reusable. Self-hosters can tune this with [`IDEMPOTENCY_KEY_TTL_HOURS`](/self-hosting/environment-variables).

## Batches

`POST /v1/send/batch` refuses the `Idempotency-Key` header with `400`. Each email of a batch takes its own `idempotencyKey` field instead, a key of the same form: an email whose key an earlier batch of your project used is not sent again, even to another recipient, and its result is `duplicate`, with the ID and contact of the email that was. Retry a batch that failed or timed out as it was, and only the emails not yet sent go out. These keys expire like the header's, and two emails of one batch cannot share one.

An email with a key is `queued` as soon as it is saved. Should Plunk's queue be unavailable at that moment, it is sent within about 20 minutes, or at once when you retry it with its key. (On a self-hosted deployment with the stalled-email sweep switched off, `EMAIL_STALL_SWEEP_ENABLED=false`, only the retry sends it.)

## Multiple recipients

`POST /v1/send` accepts an array of recipients and processes them one at a time. The key covers the request, and within it each recipient's email is sent at most once: if the request fails partway, a retry with the same key sends only to the recipients that have no email yet. A recipient listed twice gets two emails, as without a key.
